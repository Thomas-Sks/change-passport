Junction 26 · AI review of AI-written code

The Change Passport

We stop reading the code: we check a passport. The AI advises with evidence and never approves. A named person signs what they actually checked.

This page sums up the concept, what a passport contains, how it moves through review, what the demo actually proved on branch ju26-issue-2297, what runs under the hood, and where we stand.

Concept written Reference implementation running Real demo on 4 branches One-click replay, mutation testing, catching tests: built Video / presentation to do
In plain words

The idea in one minute

The problem. AI agents now write a lot of code. Humans can't read it all, and when they try, they just click "approve". An AI reviewer helps, but it misses things and sometimes it's wrong with full confidence.

Our idea. Every change comes with a passport. It says: what was asked, what the agent claims it did, and the proof for each claim. The proof comes from running the code, not from someone's opinion.

The AI helps, it never approves. It points at problems and it says "I won't decide this" when a choice belongs to a person, like a product or compatibility decision.

Risk decides how much a human reads. Simple, proven changes: a quick check. Risky changes: the human reads the parts that matter. Broken changes: sent back to the agent.

A named person signs. Not "I read everything", but "this is what was checked, this is what wasn't, this is the risk I accept". And any proof can be replayed with one click.

What happened in our demo

The agent changed 237 files. All its tests were green. With our passport, the owner had to read only 46 lines, and our proofs found that the change broke some users' builds and removed their own code from coverage. The agent's tests never saw it. The AI reviewer found 4 of the 5 problems. So the owner didn't sign: the change went back to the agent, with the proof.

The one sentence to remember

"The AI reviews, a human stays accountable, and trust comes from proof you can replay, not from the AI being confident."

2Requirement + acceptance criteriaWhat the change must do, written as 4 simple rules. Locked: the agent can't change them.We read the GitHub issue and write the rules in a small text file (YAML).
3ClaimsWhat the agent says it did, one sentence each.We copy them from the agent's README and code comments into the same file.
4PolicySorts every changed file into "boring" (generated), "normal" or "sensitive" (public API, build, security). No AI.A rules file lists folder patterns per group; a Python script matches each file to its group.
5Mechanical ruleProves 220 generated files changed only in the expected way, so nobody needs to read them.The script checks that every added line in those files is one of the 3 lines the requirement allows.
6Traceability / orphan codeEvery piece of changed code must link to a claim. One piece didn't: flagged as "orphan".The script looks for words from each claim in each changed block of code; a block with no match is an orphan.
7Acceptance testsOur own tests, written from the rules, not from the agent's code. They found 2 problems the agent's tests missed.We write small C# tests that run the code generator on a fake user project, and run them on both copies.
8End-to-end test (E2E)A real user project built with the agent's code. It confirmed both problems in real life.We build a tiny real project for two targets, then a small program looks inside the result to see what was excluded.
9Mutation testingWe undo each of the agent's 10 changes, one at a time, to see if its tests notice. Only 3 of 10: its tests are weak.A script removes one change, runs the tests, puts the change back, and repeats 10 times.
10Catching testsExtra tests written by another AI from the rules only. One passed before and failed after: it found the build break on its own.A script asks the AI to write 8 tests from the rules, runs them on both copies, and keeps the ones whose result differs.
11AI reviewerA separate AI reads the code and lists problems, quoting the exact lines. Found 4 of 5, missed 1.We give it read-only access to the code and the rules, and force its answer into a fixed format with quotes.
12RefusalsQuestions the AI must not decide and hands to a human, e.g. "should users' own code be excluded?"A fixed list of decision types (API, user-visible behaviour, compatibility…) triggers a refusal automatically.
13Lanes: green / orange / redHow much a human must read, decided by rules. This change was red because it breaks users.The script applies ordered rules: any broken rule = red, any sensitive or unproven part = orange, else green.
14Reading contractExactly what the human must read: 46 lines instead of 1,392.The script keeps only sensitive, orphan and flagged code, and drops what is already proven.
15Replay buttonOne click re-runs any proof on before and after, side by side, so you see the bug yourself.A small local web server runs the test on both copies at the same time and shows both results.
16Attestation (signature)A named person signs what was checked, what wasn't, and the risk they accept. Here: sent back to the agent.A form on the passport page; the person can only sign once every refusal is decided and every required part is ticked.
17Anti-flaky guardEvery test runs 3 times on before and after; if the result changes, it is "unstable" and never counts as proof.The scripts repeat each run and compare the 3 results.
18Assertion checkFlags tests that check nothing real: no assertion, trivial, always true, or text only. Caught the agent weakening its own test.A script reads each test method and looks for these patterns.
19Test ↔ criterion linkEach test names the rule it covers (AC-3). A rule is "supported" only if a linked test passes.The script reads the rule ID in the test name or a comment, then checks that test's result.
20Moved codeCode that was only moved is not counted as new and is removed from the reading list, with the proof.The script finds identical blocks deleted in one place and added in another.
21Seeded bugs8 typical bugs planted to test our own system, plus 1 control (moved code). It now catches all 8 and correctly ignores the move.A script adds one bug at a time on a local copy and checks whether the passport flags it.

In one line: we turned "the AI says it's fine" into "here is the proof, replay it yourself, and a named person decides".

The problem

Reading all the code no longer scales, and an AI's opinion is not enough

Review is the bottleneck

With agents, review time is up 5× and 31% more PRs ship with no review at all (Faros 2026).

Human review was already a rubber stamp

At Vercel, more than half of PRs were approved without a single comment, 18% in under 5 minutes.

AI reviewers plateau

50–60% F1 at best on real PRs. And 80% of agent-written tests check very little.

Accountability is blurry

Meta and Vercel auto-approve some PRs, but don't say who answers when an auto-approved change breaks.

What a passport contains

One document per change, which the owner reads instead of the diff

Requirement and locked criteria

4 criteria written by a human before review. The agent cannot change them. Here: 2 supported, 2 contradicted.

Agent's claims

What the agent says it did, one line each. C1 proven, C2 contradicted, C3 unproven, C4 proven but weak.

Independent evidence

Mechanical rule, acceptance tests written from the criteria, end-to-end test on a real user project, reference-assembly check, mutation testing, catching tests.

AI findings, verified

Each finding quotes the diff and gets a status after being checked against evidence. What the AI missed is shown too.

What the AI refused to decide

5 questions sent back to a human, with the reason and who decides.

Lane and reasons

Computed by written rules. Every reason is readable; no opaque score.

Reading contract

What the owner must read personally: 9 files, 46 lines out of 1,392.

Attestation

Checked and by whom or what, not checked and why, decisions taken, residual risk accepted, name and date.

How it flows

A change's path, from the agent to the signature

Declaration

Requirement ID, locked criteria, agent's claims.

Split by policy

Versioned rules file: mechanical, ordinary and sensitive zones. No AI.

Evidence

Fails before / passes after, mechanical rules, test strength, traceability, sandboxed end-to-end execution.

AI review

Different model family, full repo, mandatory quotes, closed grid, refutation before posting.

Refusal register

Public API, user-visible behaviour, compatibility, security risk, unproven claims.

Lane

Deterministic verdict engine + per-zone trust register. The AI can only raise the risk.

Signature

Questions before seeing the AI's view, required reading, refusals decided, signed attestation. The owner merges.

Measurement

Reverts and incidents per lane and zone, random counter-review, canary bugs, circuit breakers.

Where the demo differs from the target concept

  • IsolationThe "sandboxes" are git worktrees, not containers: network open for NuGet, running as the local user.
  • IndependenceAI review and catching-test generation use Claude Sonnet; the authoring agent's model family is unknown.
  • RefutationAI findings are verified by us from the evidence, not by a second refuter model.
  • HumanCriteria, decisions and the signature are played by us, for fictional people.
Review depth follows risk

Three lanes, with a human signature in each

Green

When: mechanical or ordinary code in a trusted zone, everything proven, no refusal.

Human: light check of the summary, 1–2 minutes, signed. 10% are drawn at random for a full re-review.

Orange

When: sensitive zone, unproven claim, orphan code, zone not yet trusted.

Human: upfront questions, required reading, refusals decided, signature.

Red

When: a criterion contradicted by evidence, public API, major refusal, change too large.

Human: send back to the agent with the evidence, or full read and a written decision.

Trust is earned zone by zone: 60 days without reverts or incidents and at least 90% agreement in counter-review. An incident linked to a passport suspends the zone.

Who does what

Roles

  • AgentWrites the change and declares its claims.
  • FactorySplits, proves, reviews, refuses, routes. Never approves, no merge rights.
  • OwnerNamed person for the touched zone. Decides refusals, signs, merges, stays accountable in production.
  • GuardianOwns the policy and the trust register, reviews the metrics weekly.
Not accepted

Red lines

  • No"The AI said it was fine."
  • NoA merge without a named owner.
  • NoConfidence without evidence, or a risk score nobody can explain.
  • NoA green end-to-end test presented as "the feature is done right": it only proves the criteria it covers.

What the AI found

4 findings, all confirmed by evidence. Only one misjudged: the compile break, rated "low" with 0.4 confidence.

What it missed: user code being excluded from coverage. It even stated that this was fine.

What it refused to decide

Exclude user-written code? Ship to netstandard2.0 consumers? Add a setting? Accept the docs without evidence? Is a nested class excluded only through its parent enough?

Owner's decision: sent back to the agent with evidence E3, E5, E8 and written decisions.

Limits to tell the judges

  • IsolationIn the demo, the "sandbox" is an isolated git worktree: network open for packages, running as the local user. The concept describes a disposable container with no network and no secrets.
  • CriteriaWe wrote the acceptance criteria after seeing the change. In production, they are signed beforehand.
  • StatisticsOne change analysed in depth and 8 seeded bugs written knowing the rules: an illustration, not statistical proof.
  • IndependenceThe AI reviewer is a Claude model; the authoring agent's model family is unknown.
What's next

Features to add

Research from 14/11/2026, ranked by impact on the judging criteria and feasibility in a demo. Every idea keeps a named human accountable.

1 · built

Replay every piece of evidence in one click

A button re-runs the scenario on base and branch, side by side: "before: compiles, after: CS0579". The owner can edit a line of the scenario to explore, and the replay is recorded in the attestation.

Like Replay.io's "rerecording" (same interactions replayed before / after). An AI finding without a replayable scenario stays an opinion.

Effort: medium
2 · built

"Catching" tests generated from the criteria

An LLM writes tests that pass on base and fail on the branch, making the behaviour change visible. Our E3 and E4 are exactly that, written by hand.

Meta JiTTests (FSE 2026, Oct. 2026): 74 serious bugs caught before merge, −20% incidents, 60% true positives.

Effort: medium
3 · built

Mutation testing on changed lines

Small mutations are injected into the changed code: if tests don't detect them, they are weak and the lane goes orange. This targets the only seeded bug the factory missed (S8).

Google "Practical Mutation Testing at Scale"; Meta ACH.

Effort: low to medium
4

Signature bound to the exact commit

Each explanation points to a precise diff range, and the signature is invalidated if a commit arrives after review: you can't sign a version other than the one you reviewed.

CodeRabbit Change Stack (Sept. 2026), Devin Review (Jan. 2026).

Effort: low
5

Post-merge tracking

Progressive rollout behind a flag, automatic rollback if a metric degrades, and every incident linked to the passport and the person who signed. This feeds the per-zone trust register.

LaunchDarkly Guarded Rollouts; Hud (per-function sensor, 2026). In the demo: mock-up.

Effort: medium

Judges' questions

Our answers

What would make you not trust your own output?

A canary bug passing green, a revert linked to a green passport, counter-review agreement below 90%, signatures faster than the required reading time, an AI that never refuses anything.

Who owns the decision?

The CODEOWNER of the touched zone. They sign and they merge. The AI has no approval rights.

How would this scale?

AI cost bounded per lane, reading proportional to risk, trust earned zone by zone, counter-review at 10% whatever the volume.
